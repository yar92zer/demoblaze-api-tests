# Контракт API demoblaze.com

Публичной документации у стенда нет — ни OpenAPI, ни описания эндпоинтов.
Всё, что ниже, снято разведочным прогоном `probe_demoblaze.py`: скрипт
бьёт по эндпоинтам-кандидатам, определяет HTTP-метод по ответу сервера и
печатает реальные тела запроса и ответа. Догадок и заимствований из
фронтенда здесь нет.

- **Base URL:** `https://api.demoblaze.com`
- **Фронт:** `https://www.demoblaze.com`
- **Проверено:** 9 августа 2026
- **Перепроверить:** `python probe_demoblaze.py`

## Общие правила стенда

- **Бизнес-ошибки приходят со статусом 200**, а текст ошибки — в теле, в
  поле `errorMessage`: `{"errorMessage": "Bad parameter, token malformed."}`.
  Битый токен, занятый логин, неверный пароль, отсутствующая позиция
  корзины — всё это `200 OK`. Проверять надо тело, а не код.
- **Но правило не абсолютное.** Неподходящий тип параметра стенд не
  валидирует — он падает с необработанным исключением, и Flask отдаёт
  стандартную HTML-страницу `500` вместо JSON:
  `POST /pagination {"id": "abc"} -> 500 text/html`. То есть 200 не
  гарантирован, а осмысленного кода ошибки всё равно нет: на бизнес-ошибку
  приходит 200, на кривой ввод — 500. Затронутые эндпоинты — в дефекте №9.
- `/entries` — единственный GET. Все остальные эндпоинты — POST с JSON.
- **Тело приходит как JSON, но не всегда объектом.** `/login` и
  `/deleteitem` при успехе отдают JSON-**строку** — `"Auth_token: ..."` и
  `"Item deleted."`, с `Content-Type: application/json` и кавычками в
  сыром теле. `response.json()` разбирает их штатно, но результатом будет
  `str`, а не `dict`. При ошибке те же эндпоинты отдают объект с
  `errorMessage`, так что тип тела зависит от исхода.
- Единственное место, где разбор JSON действительно падает, —
  **`/addtocart`: при успехе пустое тело и `Content-Type: text/html`**.
  Ради этого случая `CustomRequester._parse` и откатывается на
  `response.text`, если `response.json()` бросил `ValueError`.
- **Пароль передаётся открытым текстом**, base64 бэкендом не требуется:
  `/signup` сохраняет строку как есть, `/login` сравнивает её же. Base64 —
  чисто клиентская обёртка фронта. Важно лишь, чтобы регистрация и вход
  шли в одном формате.
- **Идентификатор позиции корзины генерирует клиент** — сервер принимает
  любой `id`, который прислали в `/addtocart`, и по нему же удаляет.

## Сводка эндпоинтов

| Метод | Путь | Назначение | Формат успешного ответа |
|---|---|---|---|
| GET | `/entries` | список товаров | JSON |
| POST | `/bycat` | товары по категории | JSON |
| POST | `/view` | один товар по id | JSON |
| POST | `/signup` | регистрация | JSON-строка, пустая (`""`) |
| POST | `/login` | вход, выдаёт токен | JSON-**строка** |
| POST | `/addtocart` | добавить позицию в корзину | **пустое тело, не JSON** |
| POST | `/viewcart` | содержимое корзины | JSON-объект |
| POST | `/deleteitem` | удалить позицию корзины | JSON-**строка** |
| POST | `/pagination` | следующая страница витрины | JSON |
| POST | `/check` | проверка токена, отдаёт владельца | JSON-объект |
| POST | `/deletecart` | очистить корзину пользователя | JSON-**строка** |

## Каталог

| Запрос | Тело запроса | Успех | Ошибка |
|---|---|---|---|
| `GET /entries` | — | `{"Items": [...], "LastEvaluatedKey": {...}}` | не наблюдалась |
| `POST /bycat` | `{"cat": "phone"}` | `{"Items": [...]}` | не наблюдалась |
| `POST /view` | `{"id": "1"}` | объект товара без обёртки `Items` | не наблюдалась |
| `POST /pagination` | `{"id": "9"}` | `{"Items": [...], "LastEvaluatedKey": {...}, "ScannedCount": N}` | `{"errorMessage": "Bad parameter, missing id"}` |

```
GET /entries  ->  200
{
  "Items": [
    {
      "id": 1,
      "cat": "phone",
      "title": "Samsung galaxy s6",
      "price": 360.0,
      "img": "imgs/galaxy_s6.jpg",
      "desc": "The Samsung Galaxy S6 is powered by..."
    }
  ],
  "LastEvaluatedKey": {"id": "9"}
}
```

- 9 товаров на страницу (id 1..9), пагинация через `LastEvaluatedKey`
  (ключ DynamoDB). Query-параметр `?id=9` игнорируется.
- Категории: `phone`, `notebook`, `monitor`.

```
POST /bycat   {"cat": "phone"}  ->  200  {"Items": [ ...та же форма... ]}
POST /view    {"id": "1"}       ->  200  {объект товара, без обёртки Items}
```

### Пагинация

Витрина листается отдельным эндпоинтом — это то, что дёргает фронт по
кнопкам Next и Previous. В ответе, в отличие от `/entries`, есть ещё и
`ScannedCount`.

```
POST /pagination  {"id": "9"}
  ->  200
{
  "Items": [ ...та же форма товара... ],
  "LastEvaluatedKey": {"id": "15"},
  "ScannedCount": 6
}
```

- Возвращает товары **строго после** переданного `id`, максимум 9 штук.
  `{"id": "1"}` отдаёт id 2..10, а не 1..9.
- Когда товары кончились: `Items: []`, `ScannedCount: 0`,
  `LastEvaluatedKey: {"id": "None"}` — строка `"None"`, не `null`.
- Без поля `id`: `200 {"errorMessage": "Bad parameter, missing id"}`.
- **`{"id": "abc"}` даёт `500` и HTML-страницу вместо JSON.** То же самое
  на `""`, `"1.5"`, `null` и массиве — на всём, что не приводится к числу.
  Значения `"9"`, `9`, `"-1"` и `true` отрабатывают штатно. Это не
  особенность пагинации, а общее поведение стенда — см. дефект №9.

## Авторизация

| Запрос | Тело запроса | Успех | Ошибка |
|---|---|---|---|
| `POST /signup` | `{"username": "...", "password": "..."}` | `""` (пустая JSON-строка) | `{"errorMessage": "This user already exist."}` |
| `POST /login` | `{"username": "...", "password": "..."}` | `"Auth_token: <base64>"` (JSON-строка) | `{"errorMessage": "Wrong password."}` / `{"errorMessage": "User does not exist."}` |
| `POST /check` | `{"token": "<токен>"}` | `{"Item": {"username": ..., "token": ..., "expiration": ...}}` | `{"errorMessage": "Bad parameter, token malformed."}` |

```
POST /signup  {"username": "...", "password": "..."}
  успех:  200  ""                                        (пустая JSON-строка)
  ошибка: 200  {"errorMessage": "This user already exist."}

POST /login   {"username": "...", "password": "..."}
  успех:  200  "Auth_token: cHJvYmVfN2UxMTc4Njgy..."     (JSON-строка -> str)
  ошибка: 200  {"errorMessage": "Wrong password."}
               {"errorMessage": "User does not exist."}
```

Токен — это base64 от `<username><timestamp>`, без подписи. Декодируется
обратно чем угодно, целостность сервером не проверяется.

### Проверка токена

Фронт зовёт `/check` при загрузке каждой страницы: по нему он решает,
показывать ли «Welcome &lt;username&gt;» в шапке.

```
POST /check  {"token": "cHJvYmVfNmMxYTJlNDM1YTE3ODcyNTY="}
  ->  200
{"Item": {"username": "probe_6c1a2e435a",
          "token": "cHJvYmVfNmMxYTJlNDM1YTE3ODcyNTY=",
          "expiration": 1787256}}
```

- Битый токен и **отсутствие поля `token`** дают одинаковое
  `{"errorMessage": "Bad parameter, token malformed."}`.
- `""`, `null` и массив дают `500` — см. дефект №9.
- Отдельной ручки «разлогиниться» нет: фронт просто стирает cookie.

**Важно для тестов:** пароль на фронте кодируется в base64 перед
отправкой (`b64EncodeUnicode` в `logIn()` и `register()`), а бэкенд
сравнивает строки как есть. Значит пользователь, заведённый через API
открытым паролем, через форму входа не войдёт, и наоборот. Регистрация
и вход должны идти в одном формате — это же следует из общих правил выше.

## Корзина

| Запрос | Тело запроса | Успех | Ошибка |
|---|---|---|---|
| `POST /addtocart` | `{"id": "<uuid>", "cookie": "<токен>", "prod_id": 1, "flag": true}` | пустое тело | не наблюдалась |
| `POST /viewcart` | `{"cookie": "<токен>", "flag": true}` | `{"Items": [...]}` | `{"errorMessage": "Bad parameter, token malformed."}` |
| `POST /deleteitem` | `{"id": "<uuid>"}` | `"Item deleted."` (JSON-строка) | `{"errorMessage": "Not found."}` |
| `POST /deletecart` | `{"cookie": "<username>"}` | `"Item deleted."` (JSON-строка) | `{"errorMessage": "Bad parameter, missing cookie."}` |

```
POST /addtocart  {"id": "<uuid клиента>", "cookie": "<токен>",
                  "prod_id": 1, "flag": true}
  ->  200  <пустое тело, Content-Type: text/html; json() падает>

POST /viewcart   {"cookie": "<токен>", "flag": true}
  успех:  200  {"Items": [{"id": "<uuid>", "cookie": "<username>",
                           "prod_id": 1}]}
  ошибка: 200  {"errorMessage": "Bad parameter, token malformed."}

POST /deleteitem {"id": "<uuid>"}
  успех:  200  "Item deleted."                           (JSON-строка -> str)
  ошибка: 200  {"errorMessage": "Not found."}
```

Обратить внимание: в ответе `/viewcart` поле `cookie` содержит **имя
пользователя**, а не присланный токен. `/deleteitem` токен не принимает
вовсе — только `id` позиции.

### Очистка корзины

Фронт зовёт `/deletecart` после оформления заказа — именно так корзина
пустеет по кнопке Purchase.

```
POST /deletecart {"cookie": "<username>"}
  успех:  200  "Item deleted."                           (JSON-строка -> str)
  ошибка: 200  {"errorMessage": "Bad parameter, missing cookie."}
```

- **Принимает имя пользователя, а не токен.** Это согласуется с тем, что
  в `/viewcart` поле `cookie` тоже хранит username. Вызов с токеном
  отвечает `"Item deleted."`, но корзину не трогает — позиции остаются.
- Отсюда же следует: токен не нужен, чтобы очистить чужую корзину, —
  достаточно знать логин. Та же природа, что у дефекта №4.
- `""`, `null` и массив в поле `cookie` тоже дают `"Item deleted."` —
  успех сообщается, хотя удалять нечего.

## Найденные дефекты

Дефекты публичного демо-стенда, обнаруженные в ходе работы. Описаны на
уровне наблюдаемого поведения, без деталей воспроизведения атак. Тот же
список лежит в [README](README.md#найденные-дефекты) — правки вносить в оба
файла, чтобы они не разъезжались.

| № | Дефект | Severity |
|---|---|---|
| 1 | Токен авторизации не имеет подписи и обратимо декодируется — его содержимое восстанавливается из самого токена. Проверка целостности на стороне сервера отсутствует. | Critical |
| 2 | Бизнес-ошибки возвращаются с кодом 200: некорректный токен даёт `200 OK` с текстом ошибки в теле вместо 401/400. Правило про 200 действует не всегда — на неподходящий тип параметра стенд отвечает `500` (дефект №9), так что осмысленного кода ошибки нет ни в одном сценарии. | Major |
| 3 | Пароль передаётся и сравнивается без хеширования. Кодирование на клиенте обратимо и не является защитой. | Major |
| 4 | `/deleteitem` не требует токена — принимает только идентификатор позиции корзины. Признаки IDOR. | Major |
| 5 | `/signup` при успехе возвращает пустое тело (`""`) — подтверждения операции в ответе нет. | Minor |
| 6 | Мусор в данных каталога: у товара id=9 в поле `title` хвостовой перевод строки (`"Sony vaio i7\n"`); картинки дублируются — id=4 ссылается на изображение товара id=1 (`galaxy_s6.jpg`), id=9 — на изображение товара id=8 (`sony_vaio_5.jpg`). | Trivial |
| 7 | Кнопка Previous на витрине возвращает набор со сдвигом на одну позицию. Значение `prev2` выставляется один раз при загрузке страницы (`Items[0].id`, то есть `1`) и при переходах не обновляется, поэтому `POST /pagination` всегда получает один и тот же `id`. С первой страницы Previous отдаёт товары id 2..10 вместо 1..9. | Major |
| 8 | Дублирующиеся `id` в разметке главной страницы: `id="itemc"` стоит на всех трёх ссылках категорий, `id="article"` — на описании каждой карточки товара. Невалидный HTML; выбрать элемент по `id` невозможно. | Minor |
| 9 | Необработанное исключение на неподходящем типе параметра: вместо валидации бэкенд падает, и Flask отдаёт стандартную HTML-страницу `500 Internal Server Error` вместо JSON. Затронуты `POST /pagination` и `POST /view` при `id`, который не приводится к числу (`"abc"`, `""`, `"1.5"`, `null`, массив); `POST /deleteitem` при `id` равном `""`, `null` или массиву; `POST /bycat` при `cat`, переданном массивом. `POST /addtocart` не затронут — принимает любой `prod_id` и отвечает `200` с пустым телом. | Major |
| 10 | `POST /addtocart` не валидирует `prod_id` и сохраняет что прислали. Строка `"abc"`, `"1.5"`, `null`, массив `[]` и объект `{"a": 1}` принимаются с `200` и пустым телом, после чего `POST /viewcart` возвращает эти позиции с исходным значением и исходным JSON-типом: `"prod_id": []`, `"prod_id": null`, `"prod_id": {"a": 1}`. Проверки на существование товара с таким id тоже нет. | Major |
| 11 | Подтверждение добавления в корзину различается для гостя и авторизованного пользователя: `addToCart()` в `js/prod.js` показывает алерт `Product added.` с точкой вошедшему и `Product added` без точки гостю. Одно и то же действие сообщает о себе по-разному. | Trivial |
| 12 | `POST /deletecart` определяет корзину по имени пользователя, а не по токену: тело `{"cookie": "<username>"}` очищает корзину этого пользователя без какой-либо авторизации. Логин при этом не секрет — он возвращается в ответе `/viewcart` в поле `cookie`, восстанавливается из токена (дефект №1) и выдаётся эндпоинтом `/check`. Тот же вызов с токеном вместо логина отвечает `"Item deleted."`, но корзину не трогает. Проверено: сторонний клиент, знавший только логин, очистил чужую корзину из двух позиций. | Major |
| 13 | Форма обратной связи не отправляет данные на бэкенд. `send()` в `js/index.js` очищает поля, показывает алерт `Thanks for the message!!` и перезагружает страницу; запроса с содержимым формы не уходит вовсе. Пользователю сообщается об успешной отправке сообщения, которого не было. | Major |
