# Demoblaze Test Framework

Фреймворк для тестирования публичного демо-магазина demoblaze.com на двух
уровнях: HTTP-клиент к API (`https://api.demoblaze.com`) и браузерные
сценарии на Playwright для фронта (`https://www.demoblaze.com`). Поверх
обоих — сквозные тесты, проверяющие, что слои видят одни и те же данные.

Тесты бьют по **живому публичному стенду**, а не по локальному окружению:
для прогона нужен интернет, и красный прогон может означать недоступность
чужого сервиса, а не поломку кода.

Контракт API вынесен в отдельный документ: [api-contract.md](api-contract.md).

## Стек
Python 3.11, pytest, requests, Pydantic, Playwright, Allure, pytest-xdist,
GitHub Actions

## Что покрыто

39 тестов на трёх уровнях:

| Где | Сколько | Домены |
|---|---|---|
| `tests/api/` | 14 | каталог 5, авторизация 4, корзина 3, известные дефекты 2 |
| `tests/ui/` | 22 | авторизация 6, каталог 5, корзина 5, заказ 3, контакты 2, известные дефекты 1 |
| `tests/cross/` | 3 | сквозные API + UI |

Три теста в `test_known_defects.py` — не обычные проверки, а фиксация
дефектов стенда под `xfail`; подробнее в конце раздела «Найденные дефекты».

Маркеры для выборочного прогона: `smoke`, `regression`, `negative`,
`auth`, `cart`, `ui`, `cross` (объявлены в `pytest.ini`).

## Архитектура

Два независимых слоя доступа к стенду и общий набор фикстур над ними.

**API:** `CustomRequester → Service → Tests`. Три уровня, чтобы знание об
HTTP не растекалось по тестам: тест оперирует доменными понятиями
(«добавить товар в корзину»), сервис знает про эндпоинты и формы тел, и
только реквестер — про `requests`, таймауты и Allure-вложения. Смена
транспорта или формата ответа затрагивает один уровень.

**UI:** `BasePage → Page Object → Tests`, девять классов в `pages/`.
`BasePage` держит объект страницы Playwright и таймаут, даёт обёртки
`open`, `click`, `fill`, `get_text`, `wait_visible` и
`click_expecting_alert`. Наследники объявляют локаторы классовыми
атрибутами и не дублируют ожидания. Локаторы не встречаются в тестах,
`page.locator` — тоже: тест зовёт `cart_page.get_item_titles()`, а не
лезет в разметку.

Имена слоёв разведены намеренно. Клиент к внешнему API называется
`client/`, а не `api/`, потому что рядом лежит `tests/api/` — при
одинаковых именах навигация по проекту превращается в угадайку, да и
импорты читаются хуже. UI-слой по той же логике `pages/`, симметрично
`tests/ui/`.

```
client/                 клиент к внешнему API demoblaze
  custom_requester.py   транспорт: сессия, таймауты, разбор тела, логи в Allure
  endpoints.py          пути эндпоинтов одним Enum
  services/             бизнес-операции: catalog, auth, cart
  models/               Pydantic-валидация ответов: product, cart
pages/                  Page Object'ы фронта
  base_page.py          общие обёртки над Playwright
  home_page.py          витрина: категории, пагинация, карточки
  product_page.py       карточка товара
  cart_page.py          корзина: позиции, итог, оформление
  header.py             шапка: вход, регистрация, корзина, имя пользователя
  login_modal.py        модалка входа
  signup_modal.py       модалка регистрации
  order_modal.py        форма заказа и подтверждение покупки
  contact_modal.py      форма обратной связи
utils/
  data_generator.py     уникальный логин на каждый тест
  assertions.py         assert_no_error, assert_status_code
  encoders.py           base64: encode_password, decode_token
  retry.py              with_retry поверх tenacity
tests/
  api/                  test_catalog, test_auth, test_cart
  ui/                   test_catalog, test_auth, test_cart, test_order, test_contacts
  cross/                test_api_ui — сквозные сценарии
settings.py             base_url, front_url, таймаут, ретраи — из .env
conftest.py             фикстуры обоих слоёв и хук со скриншотом при падении
probe_demoblaze.py      разведка контракта: чем снят api-contract.md
api-contract.md         подтверждённый контракт стенда
```

`conftest.py` лежит в корне, а не в `tests/`: фикстуры нужны и API-, и
UI-, и сквозным тестам, а conftest из соседней папки в другую не виден.
Там же собраны Page Object'ы как фикстуры (`home_page`, `cart_page`,
`login_modal`, …), сервисы API (`catalog`, `auth`, `cart`) и два способа
завести пользователя: `authenticated_user` — через API с токеном,
`logged_in_user` — он же, но вошедший через форму в браузере.

## Сквозные тесты

Главное, ради чего в проекте оба слоя. Обычный UI-тест проверяет, что
кнопка работает; обычный API-тест — что ручка отвечает. Ни тот, ни другой
не заметит, если браузер и бэкенд разошлись в данных. Этим занимаются три
теста в `tests/cross/test_api_ui.py`:

- **товар, добавленный через API, виден в корзине в браузере** — позиция
  создаётся `cart.add_to_cart()`, дальше вход через форму и проверка
  таблицы корзины;
- **товар, добавленный в браузере, виден в корзине через API** — обратное
  направление: клик по Add to cart, потом `cart.view_cart()` по токену;
- **цены каталога совпадают между слоями** — `/entries` против витрины.

Третий сценарий сразу поймал реальное расхождение. API отдаёт название
товара id=9 с хвостовым переводом строки — `"Sony vaio i7\n"`, это
дефект №6 в таблице ниже. Браузер же пробельные символы в тексте
нормализует, и на витрине то же название приходит как `"Sony vaio i7"`.
Сопоставление по сырому значению разваливалось на ровном месте, хотя
данные совпадали. Поэтому ключи для сверки строятся через `strip()`:

```python
api_prices = {item.title.strip(): item.price for item in catalog.get_entries().Items}
```

Это тот случай, когда падение теста — не баг стенда и не баг теста, а
разница в представлении одних и тех же данных двумя слоями. Сквозной тест
её и должен ловить.

## Запуск

```bash
py -3.11 -m venv .venv
.venv\Scripts\activate        # Windows; на Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
playwright install chromium
pytest -v
```

Браузер ставится отдельной командой — без него соберутся, но не пройдут
все тесты из `tests/ui/` и `tests/cross/`.

Отдельные наборы:

```bash
pytest                   # весь набор, 39 тестов
pytest -m smoke          # критичный минимум, 13
pytest -m regression     # расширенные позитивные проверки, 19
pytest -m negative       # невалидные данные и битые токены, 7
pytest -m ui             # только браузерные, 22
pytest -m cross          # только сквозные, 3
pytest -m auth           # домен: signup / login, 10
pytest -m cart           # домен: корзина, 8
pytest tests/api         # только API, 14 — своего маркера у них нет
```

Маркеры двух видов и не взаимозаменяемы. `smoke`, `regression` и
`negative` задают уровень: каждый тест несёт ровно один из трёх, вместе
они дают все 39. `ui`, `cross`, `auth`, `cart` задают принадлежность и
вешаются поверх уровня. Отдельного маркера `api` нет — API-тесты
отбираются путём или как `-m "not ui and not cross"` (те же 14).

Отсюда важное: **`-m regression` — это не полный прогон**, а только
расширенные позитивные проверки; негативные сценарии в него не попадают.
Полный прогон — просто `pytest` без `-m`.

Параллельно и с видимым браузером:

```bash
pytest -n 4              # параллельно, 4 воркера
pytest -m ui --headed    # смотреть, что делает браузер
pytest -m ui --headed --slowmo 500   # то же, но в замедлении
```

Прогон идёт против общего публичного стенда, но каждый тест заводит
своего пользователя, поэтому параллелится без конфликтов.

Отчёт Allure:

```bash
pytest --alluredir=allure-results
allure serve allure-results
```

**К упавшему UI-тесту автоматически прикладываются скриншот страницы и
её URL.** Это делает хук `pytest_runtest_makereport` в `conftest.py`: он
срабатывает только на фазе `call` и только если в тесте была фикстура
`page`, так что API-тесты его не задевают. Разбирать красный UI-прогон по
одному стектрейсу — занятие безнадёжное, а картинка и адрес обычно сразу
показывают, на каком шаге всё встало.

## Конфигурация

Работает без настройки — значения по умолчанию зашиты в
`settings.py`. Чтобы переопределить, скопируйте `.env.example`
в `.env`:

```ini
BASE_URL=https://api.demoblaze.com
FRONT_URL=https://www.demoblaze.com
TIMEOUT=30
RETRY_ATTEMPTS=3
```

`BASE_URL` использует клиент из `client/`, `FRONT_URL` — Page Object'ы из
`pages/`. `TIMEOUT` задан в секундах для HTTP, а для Playwright тот же
таймаут в `conftest.py` переводится в миллисекунды.

`.env` в репозиторий не попадает, в `.gitignore` он есть.

## CI

GitHub Actions, `.github/workflows/ci.yml`. Workflow `Tests` срабатывает
на push и pull request в `main`/`master`, по расписанию и вручную; в нём
четыре джобы:

| Джоба | Когда | Что гоняет |
|---|---|---|
| `lint` | каждый прогон | `ruff check .` |
| `api` | каждый прогон | `pytest tests/api -m smoke -n 4` |
| `ui` | каждый прогон | `pytest tests/ui -m smoke -n 2`, с установкой Chromium |
| `regression` | по расписанию в 06:00 UTC и вручную | весь набор, `pytest -n 2` |

Разделение на `api` и `ui` даёт быструю обратную связь: API-джоба не ждёт
установки браузера и укладывается в минуты. Полный прогон в проверку
каждого коммита не входит — он длинный и ходит по чужому стенду, поэтому
живёт на ночном расписании и кнопке workflow_dispatch.

Результаты Allure выкладываются артефактом сборки каждой джобой отдельно —
в том числе при упавшем прогоне, вместе со скриншотами.

Публикацией отчёта занимается отдельный workflow,
`.github/workflows/pages.yml`. Он запускается по `workflow_run` после
завершения `Tests`, скачивает артефакты `allure-results-*` всех джоб и
сливает их в один каталог, ставит Allure CLI и собирает отчёт
`allure generate`, после чего выкладывает его на GitHub Pages. Результат
лежит по ссылке в шапке этого файла.

Сборка отчёта вынесена в отдельный workflow намеренно: ей нужны права на
запись в Pages, а прогонам тестов — нет.

## Особенности стенда

Тесты работают против публичного демо-стенда, а не против локального
окружения. Это определило несколько архитектурных решений:

- **Бизнес-ошибки приходят со статусом 200**, а текст ошибки лежит в теле,
  в поле `errorMessage`:

  ```
  POST /viewcart  {"cookie": "definitely-not-a-token", "flag": true}
  200 OK  {"errorMessage": "Bad parameter, token malformed."}
  ```

  Битый токен, занятый логин, неверный пароль, отсутствующая позиция
  корзины — всё это `200 OK`. Проверять здесь статус-код как критерий
  успеха бессмысленно: он одинаково зелёный и на успехе, и на ошибке.

  **Но правило не абсолютное.** Неподходящий тип параметра стенд не
  валидирует — он падает с необработанным исключением, и Flask отдаёт
  стандартную HTML-страницу `500` вместо JSON:

  ```
  POST /pagination  {"id": "abc"}
  500 Internal Server Error  <!doctype html><html lang=en><title>500 ...
  ```

  То есть 200 не гарантирован, а осмысленного кода ошибки всё равно нет:
  на бизнес-ошибку приходит 200, на кривой ввод — 500. Подробности и
  список затронутых эндпоинтов — дефект №9 ниже. Отсюда разделение
  ответственности:

  - **Статус-код проверяется один раз, в транспортном слое** —
    `assert_status_code` в `CustomRequester.get/post`. Всё, что стенд
    отдаёт штатно, приходит с 200, поэтому любой другой код означает либо
    недоступность стенда, либо его падение на нашем запросе. Падать в этом
    случае надо сразу и с внятным сообщением, а не позже и не в валидации
    Pydantic-модели.
  - **Бизнес-ошибки ловятся по телу** — `assert_no_error` валит тест, как
    только в теле появляется `errorMessage`. Вызывается в сервисах (до
    сборки модели, чтобы ошибка стенда не превращалась в невнятный
    `ValidationError`) и в тестах корзины.

  Оба хелпера лежат в `utils/assertions.py`.

- **Тип разобранного тела зависит от исхода.** Тело почти везде приходит
  как JSON, но не всегда объектом: `/login` и `/deleteitem` при успехе
  отдают JSON-**строку**, а при ошибке — объект с `errorMessage`:

  ```
  POST /login       ->  200  application/json  "Auth_token: cHJvYmVfN2Ux..."
  POST /deleteitem  ->  200  application/json  "Item deleted."
  POST /deleteitem  ->  200  application/json  {"errorMessage": "Not found."}
  ```

  Кавычки в сыром теле здесь настоящие: `response.json()` разбирает такой
  ответ штатно и возвращает `str`. Поэтому сервисы не вправе считать, что
  тело — всегда словарь: `AuthService.login` работает со строкой, а
  `assert_no_error` перед проверкой `errorMessage` смотрит на тип.

  Отдельный случай — **`/addtocart`: при успехе пустое тело и
  `Content-Type: text/html`**, и вот на нём `response.json()` уже бросает
  `ValueError`. Ровно ради него `CustomRequester._parse` пробует разобрать
  JSON и откатывается на `response.text`, если не вышло. Разнобой стенда
  гасится в одном месте — транспортном слое, а сервисы получают уже
  готовое тело и не знают об этой особенности.

- **Данные не изолированы между пользователями.** Каждый тест регистрирует
  собственного пользователя со сгенерированным логином, а созданные позиции
  корзины удаляются в teardown. Это даёт возможность запускать прогон
  параллельно.
- **Документации API нет.** Контракт снят разведочным скриптом
  `probe_demoblaze.py`: он определяет HTTP-метод по ответу сервера и
  фиксирует форму запроса и ответа для каждого эндпоинта. Результат —
  [api-contract.md](api-contract.md); там же тела всех запросов
  и ответов, включая негативные.
- **Удаления пользователей в API нет**, поэтому тестовые аккаунты остаются
  на стенде. Логины имеют префикс `qa_`.

## Особенности UI-тестирования

Фронт Demoblaze — jQuery поверх Bootstrap, и это диктует, как написан
слой `pages/`.

- **Витрина и корзина рисуются скриптом.** В статическом HTML контейнер
  `#tbodyid` пуст, товары приезжают отдельным запросом уже после события
  `load`. Хуже того, при смене категории или страницы скрипт делает
  `$('#tbodyid').empty()` и заполняет заново — сразу после клика старые
  карточки ещё в DOM, и проверка «карточки видны» прошла бы на прошлом
  содержимом.

  Поэтому Page Object ждёт не элементы, а **ответ бэкенда**, и потом
  сверяет отрисованное с телом этого ответа: какие товары сервер вернул,
  такие и должны быть на экране, в том же порядке.

  ```python
  with self.page.expect_response(self._response_from(self.BYCAT_ENDPOINT)) as caught:
      self.click(self.CATEGORY_BY_NAME.format(name=name))
  self._wait_until_rendered(caught.value)
  ```

  Побочный плюс: повторный клик по той же категории не виснет. Ждать
  «пока состав изменится» здесь нельзя — он и не изменится.

  У корзины сложнее: `/viewcart` отдаёт позиции, а название и цену
  каждой строки скрипт добирает **отдельным** `/view`, и строка
  появляется в его коллбэке. Ждать приходится совпадения числа строк с
  числом позиций из ответа, а порядок строк не определён — чей `/view`
  вернулся раньше, тот и выше. Состав корзины сравнивается множествами.

- **Подтверждение покупки — SweetAlert, а не браузерный `alert`.** Это
  обычный DOM (`.sweet-alert`), читается локаторами. Обработчик диалогов
  на него не сработает — легко потратить время, гадая, почему.

- **Часть алертов синхронная.** `purchaseOrder()` и `send()` зовут
  `alert()` прямо в обработчике клика: диалог блокирует страницу, и
  `click()` не возвращает управление, пока его не сняли. Обёртка
  `expect_event("dialog")` вокруг клика в этом случае уходит в дедлок —
  она ждёт выхода из блока, а выйти нельзя. Другие алерты (`addToCart`,
  `logIn`) приходят из AJAX-коллбэка, то есть асинхронно.

  Отсюда `click_expecting_alert` в `BasePage`: обработчик вешается **до**
  клика и снимает диалог сразу, а текст остаётся сохранённым. Работает с
  обоими видами. Без обработчика Playwright закрывает диалог сам, и текст
  просто теряется.

- **Фронт кодирует пароль в base64.** `logIn()` и `register()` прогоняют
  введённый пароль через `b64EncodeUnicode`, а бэкенд сравнивает строки
  как есть. Значит пользователь, заведённый через API открытым паролем,
  **через форму не войдёт**. Фикстура `registered_user` поэтому
  регистрирует его закодированным, а в форму подставляет исходный:

  ```python
  auth.signup(username, encode_password(DEFAULT_PASSWORD))
  return {"username": username, "password": DEFAULT_PASSWORD}
  ```

  Требование одно: регистрация и вход должны идти в одном формате.

## Найденные дефекты

Дефекты публичного демо-стенда, обнаруженные в ходе работы. Описаны на
уровне наблюдаемого поведения, без деталей воспроизведения атак.

| № | Дефект | Severity |
|---|---|---|
| 1 | Токен авторизации не имеет подписи и обратимо декодируется — его содержимое восстанавливается из самого токена. Проверка целостности на стороне сервера отсутствует. | Critical |
| 2 | Бизнес-ошибки возвращаются с кодом 200: некорректный токен даёт `200 OK` с текстом ошибки в теле вместо 401/400. Правило про 200 действует не всегда — на неподходящий тип параметра стенд отвечает `500` (дефект №9), так что осмысленного кода ошибки нет ни в одном сценарии. | Major |
| 3 | Пароль передаётся и сравнивается без хеширования. Кодирование на клиенте обратимо и не является защитой. | Major |
| 4 | `/deleteitem` не требует токена — принимает только идентификатор позиции корзины. Признаки IDOR. | Major |
| 5 | `/signup` при успехе возвращает пустое тело (`""`) — подтверждения операции в ответе нет. | Minor |
| 6 | Мусор в данных каталога: у товара id=9 в поле `title` хвостовой перевод строки (`"Sony vaio i7\n"`); картинки дублируются — id=4 ссылается на изображение товара id=1 (`galaxy_s6.jpg`), id=9 — на изображение товара id=8 (`sony_vaio_5.jpg`). | Trivial |
| 7 | Кнопка Previous на витрине возвращает набор со сдвигом на одну позицию. Значение `prev2` выставляется один раз при загрузке страницы (`Items[0].id`, то есть `1`) и при переходах не обновляется, поэтому `POST /pagination` всегда получает один и тот же `id`. С первой страницы Previous отдаёт товары id 2..10 вместо 1..9. | Major |
| 8 | Дублирующиеся `id` в разметке главной страницы: `id="itemc"` стоит на всех трёх ссылках категорий, `id="article"` — на описании каждой карточки товара. Невалидный HTML; выбрать элемент по `id` невозможно. | Minor |
| 9 | Необработанное исключение на неподходящем типе параметра: вместо валидации бэкенд падает, и Flask отдаёт стандартную HTML-страницу `500 Internal Server Error` вместо JSON. Затронуты `POST /pagination` и `POST /view` при `id`, который не приводится к числу (`"abc"`, `""`, `"1.5"`, `null`, массив); `POST /deleteitem` при `id` равном `""`, `null` или массиву; `POST /bycat` при `cat`, переданном массивом. `POST /addtocart` не затронут — принимает любой `prod_id` и отвечает `200` с пустым телом. | Major |
| 10 | `POST /addtocart` не валидирует `prod_id` и сохраняет что прислали. Строка `"abc"`, `"1.5"`, `null`, массив `[]` и объект `{"a": 1}` принимаются с `200` и пустым телом, после чего `POST /viewcart` возвращает эти позиции с исходным значением и исходным JSON-типом: `"prod_id": []`, `"prod_id": null`, `"prod_id": {"a": 1}`. Проверки на существование товара с таким id тоже нет. | Major |
| 11 | Подтверждение добавления в корзину различается для гостя и авторизованного пользователя: `addToCart()` в `js/prod.js` показывает алерт `Product added.` с точкой вошедшему и `Product added` без точки гостю. Одно и то же действие сообщает о себе по-разному. | Trivial |
| 12 | `POST /deletecart` определяет корзину по имени пользователя, а не по токену: тело `{"cookie": "<username>"}` очищает корзину этого пользователя без какой-либо авторизации. Логин при этом не секрет — он возвращается в ответе `/viewcart` в поле `cookie`, восстанавливается из токена (дефект №1) и выдаётся эндпоинтом `/check`. Тот же вызов с токеном вместо логина отвечает `"Item deleted."`, но корзину не трогает. Проверено: сторонний клиент, знавший только логин, очистил чужую корзину из двух позиций. | Major |
| 13 | Форма обратной связи не отправляет данные на бэкенд. `send()` в `js/index.js` очищает поля, показывает алерт `Thanks for the message!!` и перезагружает страницу; запроса с содержимым формы не уходит вовсе. Пользователю сообщается об успешной отправке сообщения, которого не было. | Major |

Дефекты 1 и 2 зафиксированы автотестами (`test_token_is_reversible`,
`test_malformed_token_returns_error`) — тесты проверяют фактическое
поведение и упадут, если оно изменится.

Дефект №4 имеет побочный эффект для самих тестов: очистка корзины в
teardown работает именно потому, что `/deleteitem` не проверяет токен —
позиция удаляется по одному идентификатору. Если стенд когда-нибудь
починят, фикстуру `cart_with_product` придётся переписать под
авторизованное удаление.

Дефекты №4, №9 и №11 закрыты xfail-тестами в `test_known_defects.py` —
два в `tests/api/`, один в `tests/ui/`. Приём такой: тест утверждает
**правильное** поведение — что позицию корзины нельзя удалить без токена
владельца, что нечисловой `id` не должен валить бэкенд, что текст
подтверждения одинаков для гостя и авторизованного, — а `xfail` говорит,
что сейчас это нарушено. Пометка стоит со `strict=True`, поэтому если
стенд починят, тест перестанет падать, отчёт покажет XPASS, и **прогон
покраснеет**. Это и есть цель: дефект нельзя молча забыть, а его
исправление нельзя пропустить.

Так дефект остаётся видимым в отчёте как известная проблема, а не как
пропущенный или удалённый тест.
