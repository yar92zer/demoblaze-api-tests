# Demoblaze API Test Framework

Трёхслойный фреймворк для тестирования публичного API demoblaze.com.
Тестируется только API (`https://api.demoblaze.com`), без UI.

Тесты бьют по **живому публичному стенду**, а не по локальному окружению:
для прогона нужен интернет, и красный прогон может означать недоступность
чужого сервиса, а не поломку кода.

Контракт API вынесен в отдельный документ: [api-contract.md](api-contract.md).

## Стек
Python 3.11, pytest, requests, Pydantic, Allure, GitHub Actions

## Что покрыто

11 тестов на три домена: каталог, авторизация, корзина. Маркеры для
выборочного прогона: `smoke`, `regression`, `negative`, `auth`, `cart`
(объявлены в `pytest.ini`).

## Архитектура
CustomRequester → Service → Tests

Три слоя, чтобы знание об HTTP не растекалось по тестам: тест оперирует
доменными понятиями («добавить товар в корзину»), сервис знает про
эндпоинты и формы тел, и только реквестер — про `requests`, таймауты и
Allure-вложения. Смена транспорта или формата ответа затрагивает один слой.

```
client/                 клиент к внешнему API demoblaze
  custom_requester.py   транспорт: сессия, таймауты, разбор тела, логи в Allure
  endpoints.py          пути эндпоинтов одним Enum
  services/             бизнес-операции: catalog, auth, cart
  models/               Pydantic-валидация ответов: product, cart
utils/
  data_generator.py     уникальный логин на каждый тест
  assertions.py         assert_no_error, assert_status_code
  encoders.py           base64: encode_password, decode_token
  retry.py              with_retry поверх tenacity
tests/
  api/                  test_catalog, test_auth, test_cart
settings.py             base_url, таймаут, ретраи — из .env
conftest.py             фикстуры: requester, сервисы, authenticated_user,
                        cart_with_product (с teardown)
probe_demoblaze.py      разведка контракта: чем снят api-contract.md
api-contract.md         подтверждённый контракт стенда
```

Слой клиента назван `client/`, а не `api/`, чтобы не сталкиваться по имени
с `tests/api/`. Когда добавится UI, рядом встанет `pages/`.

## Запуск

```bash
py -3.11 -m venv .venv
.venv\Scripts\activate        # Windows; на Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
pytest -v
```

Отдельные наборы по маркерам:

```bash
pytest                   # весь набор, 11 тестов
pytest -m smoke          # критичный минимум, 4
pytest -m regression     # расширенные позитивные проверки, 5
pytest -m negative       # невалидные данные и битые токены, 2
pytest -m auth           # домен: signup / login, 4
pytest -m cart           # домен: корзина, 3
pytest -n 4              # параллельно
```

Маркеры двух видов и не взаимозаменяемы. `smoke`, `regression` и `negative`
задают уровень: каждый тест несёт ровно один из трёх, вместе они дают все 11.
`auth` и `cart` задают домен и вешаются поверх уровня.

Отсюда важное: **`-m regression` — это не полный прогон**, а только пять
расширенных позитивных проверок; негативные сценарии в него не попадают.
Полный прогон — просто `pytest` без `-m`. В CI на каждый коммит уходит
`-m smoke`.

Отчёт Allure:

```bash
pytest --alluredir=allure-results
allure serve allure-results
```

## Конфигурация

Работает без настройки — значения по умолчанию зашиты в
`settings.py`. Чтобы переопределить, скопируйте `.env.example`
в `.env`:

```ini
BASE_URL=https://api.demoblaze.com
TIMEOUT=10
RETRY_ATTEMPTS=3
```

`.env` в репозиторий не попадает, в `.gitignore` он есть.

## CI

GitHub Actions, `.github/workflows/ci.yml`: на push и pull request в
`main`/`master`, а также вручную через workflow_dispatch, поднимается
Python 3.11 и гоняется `pytest -m smoke`. Результаты Allure выкладываются
артефактом сборки — в том числе при упавшем прогоне.

## Особенности стенда

Тесты работают против публичного демо-стенда, а не против локального
окружения. Это определило несколько архитектурных решений:

- **Все ответы приходят со статусом 200**, включая ошибки — текст ошибки
  лежит в теле, в поле `errorMessage`:

  ```
  POST /viewcart  {"cookie": "definitely-not-a-token", "flag": true}
  200 OK  {"errorMessage": "Bad parameter, token malformed."}
  ```

  Проверять здесь статус-код как критерий успеха бессмысленно: он
  одинаково зелёный и на успехе, и на ошибке — такой ассерт не поймает ни
  одного дефекта. Отсюда разделение ответственности:

  - **Статус-код проверяется один раз, в транспортном слое** —
    `assert_status_code` в `CustomRequester.get/post`. У стенда всё
    успешное приходит с 200, поэтому любой другой код означает, что стенд
    недоступен. Падать в этом случае надо сразу и с внятным сообщением, а
    не позже и не в валидации Pydantic-модели. Это индикатор доступности,
    а не проверка бизнес-логики.
  - **Бизнес-ошибки ловятся по телу** — `assert_no_error` валит тест, как
    только в теле появляется `errorMessage`. Вызывается в сервисах (до
    сборки модели, чтобы ошибка стенда не превращалась в невнятный
    `ValidationError`) и в тестах корзины.

  Оба хелпера лежат в `utils/assertions.py`.

- **Формат ответа зависит от исхода.** `/login` и `/deleteitem` при успехе
  отдают текст, а при ошибке — нормальный JSON:

  ```
  POST /login       ->  200  Auth_token: cHJvYmVfN2UxMTc4Njgy...
  POST /deleteitem  ->  200  Item deleted.
  POST /deleteitem  ->  200  {"errorMessage": "Not found."}
  ```

  На текстовом теле `response.json()` бросает `ValueError`, а звать везде
  `response.text` тоже нельзя — ошибки того же эндпоинта приходят JSON'ом.
  Поэтому `CustomRequester._parse` сначала пробует разобрать JSON и
  откатывается на `response.text`, если не вышло. Разнобой стенда гасится
  в одном месте — транспортном слое, а сервисы получают уже готовое тело
  и не знают об этой особенности.

- **Данные не изолированы между пользователями.** Каждый тест регистрирует
  собственного пользователя со сгенерированным логином, а созданные позиции
  корзины удаляются в teardown. Это даёт возможность запускать прогон
  параллельно.
- **Документации API нет.** Контракт снят разведочным скриптом
  `probe_demoblaze.py`: он определяет HTTP-метод по ответу сервера и
  фиксирует форму запроса и ответа для каждого эндпоинта. Результат —
  [api-contract.md](api-contract.md); там же тела всех запросов
  и ответов, включая негативные.
- **Удаления пользователей в API нет**, поэтому тестовые аккаунты остаются
  на стенде. Логины имеют префикс `qa_`.

## Найденные дефекты

Дефекты публичного демо-стенда, обнаруженные в ходе работы. Описаны на
уровне наблюдаемого поведения, без деталей воспроизведения атак.

| № | Дефект | Severity |
|---|---|---|
| 1 | Токен авторизации не имеет подписи и обратимо декодируется — его содержимое восстанавливается из самого токена. Проверка целостности на стороне сервера отсутствует. | Critical |
| 2 | Ошибки возвращаются с кодом 200. Некорректный токен даёт `200 OK` с текстом ошибки в теле вместо 401/400. | Major |
| 3 | Пароль передаётся и сравнивается без хеширования. Кодирование на клиенте обратимо и не является защитой. | Major |
| 4 | `/deleteitem` не требует токена — принимает только идентификатор позиции корзины. Признаки IDOR. | Major |
| 5 | `/signup` при успехе возвращает пустое тело (`""`) — подтверждения операции в ответе нет. | Minor |
| 6 | Мусор в данных каталога: у товара id=9 в поле `title` хвостовой перевод строки (`"Sony vaio i7\n"`); картинки дублируются — id=4 ссылается на изображение товара id=1 (`galaxy_s6.jpg`), id=9 — на изображение товара id=8 (`sony_vaio_5.jpg`). | Trivial |

Дефекты 1 и 2 зафиксированы автотестами (`test_token_is_reversible`,
`test_malformed_token_returns_error`) — тесты проверяют фактическое
поведение и упадут, если оно изменится.
